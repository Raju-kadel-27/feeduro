# /send-pr-summary

Push a polished PR title and description to the open GitHub PR for the current branch.

## Steps

1. **Gather context** — run all of the following in parallel:
   - `git rev-parse --abbrev-ref HEAD` — current branch name
   - `git log $(git merge-base HEAD main)..HEAD --oneline` — commits on this branch
   - `git diff $(git merge-base HEAD main)..HEAD --stat` — files changed with ±line counts
   - `git diff $(git merge-base HEAD main)..HEAD -- '*.ts' '*.tsx' '*.sql'` — actual diff for understanding intent (read but don't quote verbatim)
   - `gh pr view --json number,title,body` — existing PR metadata (if a PR already exists)

2. **Understand the change** — read the diff and commits to understand what the change does and *why*, not just what files changed.

3. **Compose the PR** following the format below.

4. **Push via the REST API** — `gh pr edit` can fail silently when the repo uses GitHub Projects (classic); use the REST endpoint instead:
   ```
   # Get repo slug and PR number first
   REPO=$(gh repo view --json nameWithOwner -q .nameWithOwner)
   PR=$(gh pr view --json number -q .number)
   gh api repos/$REPO/pulls/$PR -X PATCH -f title="<title>" -f body="<body>" --jq '.html_url'
   ```
   If no open PR exists for the branch yet, create one first with `gh pr create --title "<title>" --body "<body>" --draft`, then edit with the REST call above.

---

## PR Format

### Title
- Concise, imperative, max 72 characters
- Pattern: `<type>(<scope>): <what it does>` — e.g. `fix(api-keys): prevent cross-org deletion`
- No trailing period

### Body (GitHub-flavoured Markdown — must render well)

```markdown
## What changed

<2–4 sentences in plain English. Explain the problem that existed, what you changed, and the effect. No bullet points here — write it like a paragraph a teammate would read.>

## Why

<1–2 sentences on the motivation. Omit if already obvious from "What changed".>

## Changes by area

- **`path/to/file.ts`** — plain English description of what changed in that file and why
- **`path/to/other.tsx`** — same pattern; one line per logical group, not per file if multiple files serve the same change

## Test plan

- [ ] <specific thing to verify manually or in CI>
- [ ] <another check>
```

### Rules for the body
- Write descriptions in plain English — avoid jargon, avoid restating the code
- Group files by concern, not one bullet per file
- Keep "Changes by area" entries short (one line each); the details live in the diff
- "Test plan" items should be concrete and checkable, not vague ("verify it works" is not acceptable)
- Do not include "Generated by Claude" or any AI attribution
- Do not use the `Co-Authored-By` footer
